# 기획서 Description 작성 규칙

CPO BO 기획서 6건(162셀)의 실제 description을 분석해 정리한 관례다. 팀 공통 규칙이 문서로 있는 것은 아니므로, **고치려는 문서에 이미 있는 습관이 이 문서보다 우선**한다. 기존 문구는 그대로 두고, 필요한 부분만 덧붙인다.

## 우선순위: 이 스킬은 보조다

이 스킬은 보조 목적이다. 기획자의 기존 작업 방식, 문체, 설정, 지시와 이 문서의 규칙이 충돌하면 **기획자의 방식을 우선**하고 이 문서의 규칙은 따르지 않는다. 충돌이 의심되면 기획자에게 어느 쪽을 따를지 확인한다.

## 먼저 확인: CPO BO 작업인가

이 규칙은 CPO BO 기획서용이다. 기획자가 "CPO 요건이야"처럼 직접 말하면 그대로 적용한다. 말하지 않았다면 아래 단서로 판단한다.

- Confluence 스페이스 키가 `CPO`이거나 CPO 기획서 링크를 다루고 있다
- 두레이 요건이나 대화에 CPO BO 화면명(상품전시관리, 주문관리, 매입 현황관리 등)이 나온다
- 이 대화에서 이미 CPO BO 작업을 하고 있다

단서가 다른 프로젝트(예: HMG Board, 멤버십, 그룹웨어)를 가리키면 이 규칙을 적용하지 않고 그 사실을 알린다.
단서가 없어 판단되지 않으면 적용하기 전에 기획자에게 어느 프로젝트인지 한 번 묻는다.

## 1. 기본 형태

- 한 셀은 그 화면(또는 팝업) 하나의 완결된 스펙이다. 문단이 아니라 **중첩 불릿 트리**(3~5단)로 쓴다.
- 첫 줄은 이름표다. `**[명칭]**`, `* **소제목**`, `* 화면설명` 중 대상 문서가 쓰는 형태를 따른다.
- 다른 기획서에 상세가 있으면 `상세 내용 : {기획서명} 참고.` 한 줄로 위임해도 된다.

## 2. 문체

| 종결 | 비중 | 쓰는 곳 |
|---|---|---|
| 명사 종결 | 74% | 기본형 (`디폴트: 전체`) |
| `-함/-됨/-음` | 7% | 강조하거나 규정할 때 (`노출함`) |
| 존댓말 | 3% | 화면에 뜨는 문구를 인용할 때만 |
| `-한다` 평서 | 거의 0 | 쓰지 않는다. 공통 UX 위임 문장(`공통UX 정의를 따른다`)만 예외 |

따옴표와 괄호는 의미를 가른다.

| 표기 | 의미 |
|---|---|
| `[대괄호]` | 버튼, 메뉴 |
| `‘홑따옴표’` | 상태값, 선택값 |
| `“겹따옴표”` | 화면에 그대로 노출되는 문구 |
| `{중괄호}` | 런타임에 치환되는 변수 |

주체를 쓸 때는 `운영자`, `사용자`, `담당자`로 쓴다.

## 3. 구성 순서

- **목록 화면**: 화면 목적 한 줄, 숏컷(간편조회), 검색조건, 리스팅 상단(건수, 정렬, 액션 버튼), 리스팅 컬럼, 페이징.
  리스팅 컬럼은 `컬럼명 : 값의 출처` 형식으로 한 줄씩 쓴다. 출처를 반드시 밝힌다.
- **팝업과 버튼**: 트리거, 유효성, 성공, 실패, 닫기 순이다. 성공 처리는 `(1) 화면 갱신 (2) 로그 기록 (3) 데이터 반영`처럼 번호를 붙인 부작용 목록으로 쓴다.

## 4. 어디까지 쓰나

**쓴다**: 상태값 전체와 각 정의, 검색 매칭 방식(exact, like), 플레이스홀더 문구, 디폴트값, 정렬 기준, 입력 제약(자릿수, 필수), 버튼 활성과 비활성 조건, 파일명과 엑셀 서식, 날짜 포맷, 값 예시(`예)`), 백엔드 연동 지점(업무 명칭으로), 분기 근거가 되는 에러코드.

**쓰지 않는다**: px, 폰트, hex 색상, API 경로와 HTTP 메서드, 레이아웃을 말로 설명하는 문장(배치는 UI 이미지의 몫), `~하는 것이 좋다`류 권고. 색은 `색상 강조 필요`, `붉은색으로 표시`처럼 요구 수준으로만 쓴다.

## 5. 예외와 엣지케이스

- **유효성**은 번호 붙인 케이스 목록이다. 형식은 `(n) 조건: “노출 문구”`다. 검증 순서가 있으면 순차 검증이며 앞에서 오류가 나면 이후는 진행하지 않는다고 명시한다.
- **얼럿**은 `“문구” [버튼][버튼]`에 버튼별 후속 동작을 붙인다. `[취소]: 얼럿 닫음.`
- **실패와 부분 실패**는 롤백 여부를 명시한다.
- **빈 상태**는 무엇을 대신 노출하는지로 쓴다. (`-`, `정보없음`, `파일없음`)
- 얼럿 문구는 명사 종결 비중을 적용하지 않는다. 존댓말 문장으로 쓴다.

## 6. 관용 표현

| 상황 | 표현 |
|---|---|
| 조작 트리거 | `클릭 시,`, `선택 시,` |
| 보이게 함 | `노출`, `표기`, `표시` |
| 안 보이게 함 | `미노출`, `노출 안함` |
| 기본값 | `디폴트 :` |
| 조건부 노출 | `노출조건:` |
| 입력 검증 | `유효성체크` |
| 버튼 잠금 | `비활성화`, `disabled 상태` |
| 닫기 | `얼럿 닫음.`, `팝업 닫음` |
| 저장 후 | `화면 새로고침` |
| 다른 화면 참조 | `{화면}> {영역}> {항목}` |
| 공통 규칙 위임 | `공통UX 정의를 따른다` |
| 개발 확인 요청 | `개발확인필요`, `개발 협의 필요` |
| 부연 메모 | `(참고)` |
| 삭제된 스펙 | `~~취소선~~`에 `스펙아웃` |

틀린 내용을 조용히 지우지 않는다. 취소선으로 남기고 옆에 새 내용을 쓴다. 변경 근거 티켓은 문장 끝에 `KQ-#####` 라벨로 붙인다.

## 7. 🚨 지어내지 않는다 (가장 중요)

형식이 완벽하면 사람이 덜 의심한다. 틀린 스펙이 형식을 갖추면 그것이 최악이다. 실제로 이런 사고가 있었다.

| 쓴 것 | 원본 |
|---|---|
| "성공 건은 롤백하지 않음" | "1건이라도 실패 시 전체 업로드 불가" |
| "견적 0건이면 승인 불가" | "0건이거나 0원이어도 승인요청 가능" |
| 노출 조건이 상품화센터 선택 시 | 적치장 선택 시 |

**규칙 세 가지**

1. **원본이 위임한 것은 위임으로 남긴다.** 원본이 `목록 검색조건 참조`라고 했다면 그 자리에 값을 지어내 채우지 않는다. `{화면}의 {영역} 참조`로 쓴다.
2. **값 집합, 문구, 수치는 근거가 없으면 채우지 않는다.** 상태값 목록, 얼럿 문구, 글자수 제한, 최대 건수, 정렬 기준과 디폴트가 해당한다. 요건에 없으면 `{미정: 최대 업로드 건수}` 또는 `“{미정: 문구}”`로 남긴다. 그럴듯한 문장을 만들지 않는다.
3. **분기 로직은 원천에 없으면 쓰지 않는다.** `~인 경우 불가`, `~하면 롤백` 같은 규칙 문장은 사실 주장이다. 근거가 없다면 `(개발 협의 필요)`로 남긴다.

**다 쓴 뒤 자가 점검**

1. 단정형으로 쓴 규칙 문장(`~함`, `~불가`, `~됨`)을 전부 짚는다.
2. 각각 원천 문장이나 현행 기획서를 댈 수 있는지 확인한다.
3. 못 대는 것은 `{미정: …}` 또는 `(개발 협의 필요)`로 바꾼다.
4. 가정한 값이 있으면 기획자에게 목록으로 알린다. 미확정을 남기는 것은 실패가 아니고, 지어낸 확정이 실패다.
